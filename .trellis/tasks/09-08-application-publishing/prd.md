# 应用层：分享、博客与主题 — PRD

## Goal

将分享授权、博客发布与互动、群组、用户主题及预览的业务决策收敛到应用层。保留现有公开页面、URL、表单/JSON/JSONP 外形、用户上传主题与数据语义；不能以迁移为由公开私有内容或把部分写入报告为成功。

## 已确认事实与依赖

- 父任务 `09-08-business-layer-architecture/design.md` 的应用轨道为 identity → notes → content → publishing → admin。本叶只直接依赖已归档的 `domain-contracts`；identity 的 principal/session、admin 邮件 outbox 是集成契约，不是本叶的元数据依赖。
- `conf/routes` 含 `/share/:action`、`/blog/*`、`/preview/*`、`/member/blog/:action`、`/member/group/*` 和 `/note/setNote2Blog`。旧 `ShareNote`/`ShareNotebook` 只有创建时间，没有到期字段或到期校验；原“过期分享”仅见于旧任务验收表述，并非已经存在的运行行为。本次将其列为新增的分享授权能力，而非假称旧功能回归。
- notes/content 任务约定：note、图片/附件、PDF 消费分享 read/update permission port；notes 拥有 note mutation/USN/receipt，content 拥有通用安全文件/图片/归档 primitive。归档状态不代表跨层真实环境证据通过。
- 遗留实现的无 owner ID 查询、先删后插、部分失败后仍返回成功、仅字符串过滤 ZIP/path 等均为待修缺陷，不能作为安全兼容基线。证据见 `research/spec-audit-2026-09-23.md`。

## 业务、边界与数据要求

### PB-01 分享与群组

1. 授予/修改必须使用已认证 actor，确认 note/notebook 当前归属于该 owner 且不是已删除/回收站资源；仅 owner 能授予或修改他人的读写权限。被分享方只可退出自己的授权，不得通过伪造 owner/recipient 删除他人权限。`Perm` 只允许 `0`（读）、`1`（更新）；无效 ID、空邮件、未知用户、自分享、非授权范围的组不能写入。
2. 有效权限须同时校验 owner、资源状态、直接 recipient 或当前组成员身份及 grant。访问时先排除已经到期的 grant（在到期瞬间及之后不能凭该授权查看或更新）；再按资源级别（note 覆盖 notebook）、同级别个人显式授权覆盖组授权合成；仅在同一资源级别、没有个人授权且有多个有效组授权时取权限更大的值：任一组 `Perm=1`（可更新）则结果为 `1`，否则有 `Perm=0`（只读）则为 `0`，均无有效授权则拒绝。到期 grant 不能遮蔽其他独立且仍有效的授权；上层级的有效只读授权仍覆盖下层级的可写授权，不以“权限更大”跨层级合成。不得依赖 DB 返回顺序。到期、撤销、退组、删除组须依当前有效关系重算，对分享列表、note/asset/PDF 读取与更新生效；DB 错误不得当作授权或成功空列表。
3. 同一 owner/resource/recipient 重复授予、修改并发不得出现重复有效关系或先删后插的无授权空窗。`HasShareNote` 是可核对的辅助投影而非第二授权来源；grant、投影、组关联清理在中断/未知提交时须可恢复。任一步失败显式返回失败或 `partial_write`，禁止固定成功。唯一索引须以实际 index preflight 证明，不能凭模型注释推断。
4. 多 email 分享沿用 `email -> info.Re` 的逐人结果外形，各项独立反映成功、未知用户、自分享、权限/写入失败；不把部分成功冒充整批成功。分享清单、内容和收件人资料只向有权 actor 暴露。分享者可对每条个人/组的 note/notebook 授权选填独立到期时间；创建时未填则不过期，旧记录缺字段也不过期，不能从 `CreatedTime` 推定期限或在升级后批量失效。期限输入采用具体日期时间，界面按使用者时区展示，服务端统一以 UTC 持久化和比较；不采用相对时长预设。新建、延长、缩短、续期时显式提交的期限必须严格晚于服务端当前时刻；等于或早于当前时刻的输入拒绝且不更改授权，立即停止访问须撤销分享而非提交过去时间。仅该分享 owner 可以**显式**延长、缩短或取消某条授权的期限，包括在到期后续期；续期/取消期限的写入得到确认后才重新授权，失败或未知提交不得假报成功、不能先放行。旧版仅改权限的请求未提供到期字段时须保留该授权已设置的期限，不能隐式续期；旧有记录即使已过期也不因更新其他属性重新校验并拒绝，除非显式提交新期限。到期时间须可持久化并在每次服务端授权/访问时判定，不依赖后台定时任务或 Mongo TTL 删除；数据尚在库内不代表可以访问，已下载或客户端缓存的副本不能追溯撤回。
5. Q-P1 输入合同已决：沿旧分享创建/改权及组授权动作增加可选 `expiresAt`，须为精确到秒、带 `Z` 或数值时区偏移的 RFC3339 绝对时刻；不接收无偏移、本地格式、小数秒、空白值或非法日历时间。服务端将合法值按 UTC 存储/比较，只对**显式提交**的新期限校验严格晚于服务端当前时刻。未提供 `expiresAt` 时，创建无期限、更新保持原期限；仅更新已有授权时可用独立的 `clearExpiresAt=true` 显式取消期限，不得以空白值或缺字段隐式清除。两个字段同时提供、`clearExpiresAt` 非 `true` 或创建时清除一律拒绝，不更改原授权及计数。对个人批量 email 创建，一个请求给定的期限应用于各收件人的独立 grant；无效日期/参数组合应在逐人写入前拒绝，成功的逐人结果仍保持原外形。分享界面按使用者时区展示/输入本地截止时间及明确时区提示，并转换为带偏移的绝对时刻提交；夏令时跳过或重复等无法无歧义表示的本地时间须拒绝或要求选择明确偏移，不得静默滚动到另一时刻。清除既有期限须有独立的明确操作，清空输入框不等于清除；错输/失败应保留原权限和期限。旧客户端完全不带新增字段时保持旧创建/改权语义与成功响应。

6. 以上“创建无期限”只适用于 `(owner, resource, recipient)` 不存在授权的情形；旧 `AddShareNote/AddShareNotebook` 或组 Add 再次命中已有 grant 时属于更新，省略 `expiresAt` 必须保留原期限（含已过期），不得借重复授予清空期限。显式新期限按 owner/时间校验更新；`clearExpiresAt=true` 仅命中已存在的 grant 时允许。混合已有与新 recipient 的批量创建若携带清除标志，须在任何人写入前拒绝整批请求；旧无字段重复 Add 的原权限修改/响应外形保留，但不使已设期限隐式失效。

7. 授权数据合同：`ShareNote` 与 `ShareNotebook` 均使用可选 `ExpiresAt time.Time`，BSON key 为 `ExpiresAt`，以 Mongo BSON DateTime 按秒级 UTC 归一化；字段缺失或 `null` 表示永久有效。访问控制不使用 TTL 删除。索引 preflight 发现历史重复时必须报告冲突并阻止静默排除或删除；迁移/回滚不得把缺字段改成过期，也不得用 `CreatedTime` 推导期限。

8. 现有 `GroupService.IsExistsGroupUser` 与 `GetMineAndBelongToGroupIds` 将组 owner 视为有效成员，即使没有 `GroupUser` 文档；本任务按此兼容语义冻结：owner 可获得该组授予的权限，不能通过普通成员删除动作移除 owner 身份，删除组才终止该成员资格。实现不得要求为 owner 补写伪 `GroupUser` 记录。

9. 分享唯一性按集合和收件人类型分别约束，不以包含两个可选收件人字段的普通复合索引代替。`share_notes` 的个人键为 `(UserId, NoteId, ToUserId)`、组键为 `(UserId, NoteId, ToGroupId)`；`share_notebooks` 分别为 `(UserId, NotebookId, ToUserId)`、`(UserId, NotebookId, ToGroupId)`。个人唯一索引的 partial filter 仅要求 `ToUserId` 为 BSON ObjectID，组索引仅要求 `ToGroupId` 为 BSON ObjectID；**不能**在 partial filter 用 Mongo 不支持的 `$exists:false` 表达互斥。每条 grant 必须有且仅有一个非零、真实的收件人 ObjectID，另一字段缺失，此约束由写入校验、preflight 和集合 JSON Schema validator 共同执行；不接受双字段、空/零 ID、`null` 或错误类型。查询收件人清单另设 recipient-leading 索引，`HasShareNote` 仅按 `(UserId, ToUserId)` 唯一约束，不能成为权限来源。具体集合、索引名称和 preflight 报告见 `design.md`“分享索引合同”。上线前枚举两类重复键、双收件人/无收件人/非法类型与旧索引冲突，报告集合、索引、键摘要和冲突数并阻止就绪/启动；不得自动删除、排除或任选赢家，修复须经单独的数据核对与授权。

### PB-02 公开博客和互动

1. 公开内容与匿名可读资源必须统一使用有效 owner、`IsBlog=true`、`IsTrash=false`、`IsDeleted=false` 的发布谓词；按 ID、slug/UrlTitle 与单页查询都校验 URL 所指定的 owner（无 owner 参数的公开 permalink 除外）。撤销发布、回收站和删除后列表/详情/搜索/统计/图片引用不得泄露私有内容。自定义域名/子域名解析不得把 host 与别人博客串线。
2. `/note/setNote2Blog` 批量与 notebook 发布传播须调用 notes 的 USN/receipt 合同；发布/取消发布失败不得返回固定 `true`。逐项结果及部分写入内部可观测，沿用旧公开响应字段，不重新实现 notes 的 operation identity。标签、摘要、推荐和计数 projection 不得与主记录可见性相矛盾。
3. 匿名可以读取已发布页面和公开统计；评论、回复、点赞、评论点赞和删除评论须已认证。本站 `CanComment` 与 `CommentType` 不允许被直接请求绕过；回复必须属于同一已发布 note。评论作者、博客 owner 或管理员才可删评论；点赞 toggle、阅读/评论计数仅在相应提交成功后更新。沿用既有作者/被回复者的应通知对象判定：存在应通知对象时，评论/回复记录、计数与**持久化通知意图**必须一起确认才返回提交成功；入队失败不得留下可见的成功评论或新增计数，也不能发信。无应通知对象时无需伪造通知事件，评论与计数仍须一同成功。未知提交不得假报成功，重复请求/重试不得造成重复通知意图；邮件发送失败由持久化意图重试、可观测，不撤销已提交评论，也不向请求方声称邮件已投递。若平台无法保证这组操作的可恢复一致性，必须显式失败而非退回无结果 goroutine；重复/并发与错误不产生伪成功。
4. 保留 `UserBlogBase`、`UserBlogComment`、`UserBlogStyle`、分页/排序、单页顺序与 URL title、当前 JSON 字段；区分“字段未提供”和“显式空/false”，不以 Go 零值擦除未提交字段。`BlogComment.ToCommentId` 的历史 BSON key `ToCommendId` 不得顺手迁移。评论正文统一为纯文本；输入中的 HTML 标签是文字，不作为富文本解析、不在保存时丢弃标签；新旧评论在博客页面和预览中须按输出上下文安全编码，显示字面标签而不执行脚本，通知邮件含评论正文时同样不得解释为 HTML。JSON/JSONP 正文字段保留原文本值，由最终展示端进行转义，不因传输层预转义导致双重编码。新提交的评论/回复必须是合法 UTF-8 且不全为 Unicode 空白；按原输入计数最多 2000 个 Unicode 码点，编码后最多 8 KiB（8192 字节），超过任一上限直接拒绝，不截断、不写入/更新计数/发送通知。空白只用于校验而不擅自裁剪正文；历史评论无论原长度均保持原文，仅按纯文本展示。
5. 公开 JSONP 入口收到的 `callback` 只接受完整匹配的有限长度 JavaScript 标识符或点式路径；输入不得包含调用表达式、括号、引号、空白、转义或其他可执行语法。可接收的 ASCII 标识符子集为 `[A-Za-z_$][A-Za-z0-9_$]*`，可用 `.` 连接多个非空片段，总长度上限 128 字节（ASCII，含点）；空值、超长及 `cb(1)` 等非法值必须拒绝，不能原样输出为脚本、静默降级为 JSON 或执行任何互动副作用。合法 callback 的 JSONP body、Content-Type 与旧字段形状维持；`GetComments` **未提供** callback 时仍走原 JSON 分支，显式空值不能当作未提供。此项有界收窄是 Q-P5 已批准的安全兼容例外，具体 HTTP 错误 status/body 由 interface 基于旧适配行为联审并在真实请求中冻结。
6. Q-P8b 已决：评论被有权者成功删除且停用已确认后，关联的**未越过持久发送交接闸门**的通知不得再交给邮件服务；已越过闸门或已成功发送的消息无法承诺追溯撤回。即使待发事件已被 worker 领取，只要删除取消先赢 CAS，仍须阻止继续发送；交接 CAS 先赢则不能声称取消成功。删除请求的开始时间并非成功取消时间；若闸门先赢但 SMTP 尚未实际接受，旧 bool 响应仍不得虚报已取消，须返回失败/未知并保留内部诊断。删除与停用结果必须可确认，失败或未知提交不得把可能继续发送的通知报告成已取消；不得仅凭评论记录硬删除就假定通知已停发。

7. Q-P9 已决：评论和回复的 `CommentPost` 请求必须携带 `submissionId`，为本次有意提交新生成的 128-bit 随机值，以 32 位小写十六进制字符串传递；网络重试沿用同一值，有意再次发表（即使正文完全相同）必须使用新值。缺失、空值、格式错误的身份在任何评论、计数、通知写入前拒绝；**不兼容**不携带该字段的旧评论客户端，也不得以正文、作者和时间窗口推断身份。服务端以已认证 actor 和 `submissionId` 标识唯一提交，并将其绑定 note ID、reply ID 和原始正文摘要：同一身份同一请求重复提交返回已确认的同一评论结果，不新增评论、计数或通知；同一 actor 重用该身份提交不同内容或目标必须报冲突、零写入。评论/计数/必要通知意图与可查询的提交凭据共同可确认提交；未知结果重试只能以同一身份核查/恢复，不得重新生成 ID 假冒新提交。已删除评论的凭据保留停用/墓碑语义，重试不得重建或重新发信；读回失败不得假报已提交或未提交。Q-P8 的单次提交与 admin 投递合同同时适用，详见 AC-PB4-RETRY。

8. 所有博客互动必须绑定真实资源：`DeleteComment` 必须确认评论的 `NoteId` 等于路径中的 `noteId`；`LikeComment` 必须同时确认 actor、评论所属 note、已发布谓词和点赞开关；评论列表、统计、点赞和阅读数不得泄露私有、回收站或删除 note；回复目标必须存在、属于同一 note 且满足公开谓词。请求中的 comment/reply/recipient 不得作为可信归属来源。

9. `/note/setNote2Blog` 当前公开响应为原始 JSON boolean。实现必须先收集每个 note 的 notes mutation/USN/receipt 结果；仅当所有目标均确认成功时才返回 `true`，任一失败、未知提交、权限失败或部分写入均返回 `false`，并保留内部可诊断逐项结果。`false` 不承诺自动回滚；部分写入必须可由 receipt/对账路径定位和修复。不得改变既有 raw boolean wire shape。

10. 博客写入与投影必须零伪成功：`UpateBlogUrlTitle`、`UpateBlogAbstract` 及单页增删改排序不得用先清空、多写后覆盖或忽略第二写入结果的方式报告成功；排序输入必须是当前已有 single ID 的完整合法排列，未知、重复、缺失 ID 或任一投影写失败均零写入或显式 `partial_write`，并提供修复/对账路径。

11. 评论提交凭据完整保留至少自可确认终态 `TerminalAt` 起 30 天；删除后若较晚，再从确认删除的 `DeletedAt` 起满 30 天。此期限只允许压缩非身份/恢复负载，不能使同一 `(ActorId, SubmissionId)` 在任意时间被当作新提交：保留最小永久墓碑/凭据，包括身份、目标、原文摘要、comment ID、终态/删除标记与足以核对原结果的最小引用。`pending`、未知提交、对账中、关联 outbox 非确定终态以及仍可人工重试的 `dead` 均不得清理；不使用自动 TTL。publishing 维护任务按有界批次、幂等 CAS/读回压缩，失败重试并报警；索引/存储随累计提交线性增长，必须监控数量与字节、定期容量规划，容量不足显式拒绝新提交，不能静默淘汰身份或声称无限期恒定容量。详情及验收见 `design.md`“评论凭据保留与 GC”。

12. 评论通知采用 `unconfirmed → pending/retry → claimed → handoff_pending → handed_off → sent` 的受控路径，并有 `cancelled`、`dead`、`handoff_unknown` 分支。只有已确认提交才可领取；删除与交接对同一 comment/recipient 事件进行持久版本 CAS 裁决，成功取消未交接事件后 worker 不得使用旧快照发送；未知结果读回失败不能当取消成功。SMTP 调用与 Mongo CAS 不能组成一个原子事务，`TransportHandedOffAt` 表示不可撤回的**持久发送交接闸门**，不表示 SMTP 接受；闸门后进程崩溃或 transport 结果不明必须进入 `handoff_unknown`，禁止自动重发或把邮件标成已送达。删除先赢 CAS 时停发，交接先赢时不承诺召回；完整迁移、错误与对账见 publishing/admin 双方 `design.md`，不能把物理 SMTP 接受时刻伪称数据库原子事实。

### PB-03 主题及预览

1. 三个内置主题 `default`/`elegant`/`nav_fixed` 与既有 style 路径维持对应；用户主题必须 owner scoped，每用户至多一个 active，博客设置 ThemeId 指向同一有效主题。**管理员及普通用户均可上传合法的自有 HTML/JS 主题、显式启用并在自己博客实际使用**，仅导入成功或显示在主题列表中不算完成。任何账户上传/自用均不自动公开；仅经管理员对其自有、已完成验证的主题**显式公开**后，其他已认证用户才可在可安装列表看到并主动安装。仅管理员能公开/取消公开自有主题，公开/取消公开不替管理员切换 active，也不自动替其他用户安装；未经公开的主题即使知道 themeId 也不得跨账户安装。内置主题原件不可被普通用户修改、他人主题不可编辑/导出；删除 active theme、非法模板/配置须可定位而不泄露绝对路径。
2. 模板、图片及 ZIP entry 只接受经统一校验的相对逻辑路径：拒绝 `../`/`..\`、绝对/盘符/UNC、symlink/junction 和间接越界，所有读写限制在当前 owner 的 canonical root。ZIP 解压前后验证条目类型/布局、重名、展开预算与目标根；失败不留下可通过静态路由读取的半包。Q-P6 已确认保留单包压缩大小不超过 10 MiB、主题常规文件不超过 100 个及现有图片上传 5 MiB 上限；每个 ZIP 常规文件实际展开不超过 5 MiB，所有常规文件实际展开合计不超过 20 MiB，目录和文件条目总数不超过 200，移除允许的单个主题顶层文件夹后规范化相对路径最多 8 层。解包中持续计算实际读取字节与条目数，超限立即拒绝、清理未公开暂存且不新增/激活/公开主题；各边界以“等于上限允许，超过拒绝”为准。不另设压缩比阈值，不能因此绕开其余预算。
3. `theme.json` 必须合法并满足 `Theme.Info` 可 JSON 编码；模板图检查引用、循环、语法失败，不得静默换别的主题或向匿名用户输出文件系统细节。文件+数据库 metadata/active 的多步写入要可恢复，不凭某一步成功报告整体成功。图片使用 content 已有图片校验/存储 primitive，不能信任扩展名或原始文件名。
4. 其他用户的安装操作须再次确认来源仍是管理员显式公开的合法主题（另保留既有内置主题选择），将文件和 metadata 复制到安装者自己的主题空间并按旧行为自动启用，核对其 `IsActive`、`UserBlog.ThemeId` 与实际博客渲染一致；导入/公开/安装/激活任一步失败均不返回假成功，不得留下可安装半包或破坏旧 active。管理员取消公开后不得新安装，但既有已安装副本为用户自有文件与记录，仍可使用，不能随来源下架而撤销。
5. 预览只用当前认证用户拥有的主题，允许以未激活的自有主题渲染**已发布内容**，不要求先激活或公开该主题；不信任 URL 中的他人 userId，不修改主题 active 或内容实际公开状态。预览列表、搜索、标签、分类、文章详情和单页须复用正式博客的有效发布谓词和 owner 约束，未发布草稿、撤销发布、回收站或已删除内容即使是当前用户本人也不能通过预览读取，不新增草稿专用预览路由。主题保持重构前的运行形态：ZIP 导入程序根目录下当前用户的 `public/upload/<Digest3(userId)>/<userId>/themes/<themeId>`，博客与预览依现有 URL/Host 渲染其 HTML 模板，CSS/JS/图片由原静态路径服务，不新增隔离域、强制跳转或新的跨域登录/评论流程。上传不自动“公开”仅指未列入可安装主题及不能由其他用户安装，**不意味着文件路径自动成为私有资源**。普通用户上传可执行 HTML/JS 在同源访问场景下的风险已知且需记录，不能把保留旧行为误写成已实现跨账户脚本隔离；owner、文件路径和服务权限校验仍须按本规格修复。

6. 自定义主题的编辑、导出、删除和文件读写始终限定为 `(ownerID, themeID)`；管理员也只能操作自己拥有的自定义主题，不能跨 owner 编辑、导出或删除，内置主题只读。非 active 主题删除成功后必须同时清理其 metadata、文件树和静态可读入口；删除或导出遇到失败/未知提交必须可读回或进入可恢复状态，不得留下静态孤儿。导出临时目录必须位于当前 owner 的主题根或受约束的 owner 临时根，下载名须清理并限制在该根内，临时文件清理失败必须显式记录，不得把任意 `Theme.Name` 拼接为路径。

7. `theme.json` 的 `Name`、`Version`、`Author`、`AuthorUrl` 若存在必须为字符串；其他不符合 `Theme.Info` 合同的值必须返回可识别的 `validation/template_invalid`，不得因 Go 类型断言 panic。主题导入、激活、公开、安装、删除、导出任何一步失败都不得留下 metadata/文件/active 的不一致或可静态读取的半包；未知状态须先查证再补偿。

## 兼容与错误边界

- 不新增隔离来源或强制跳转，不更名旧 `/blog`、`/preview`、主题静态 URL、模板 key 和合法 JSON/JSONP 响应；原 URL/Host 页面与其他登录互动维持旧外形。Q-P5 是明确的安全兼容例外：非法 callback 不再原样插入脚本。Q-P9 是**仅评论/回复提交**的请求兼容例外：`CommentPost` 必须提供 `submissionId`，旧无身份客户端失败；不顺带改变分享期限的旧客户端合同或其他互动输入。除可确认提交凭据所必需的有界持久化外，不做无关 schema 迁移。`/blog` 无 owner 参数时沿用管理员博客归属，公开 ID/slug 与自定义域绑定仍须校验。方法、Content-Type、状态/重定向与历史 Golden 由 HTTP adapter 做真实 replay；服务单测不代表 HTTP 兼容通过。静态资源路径和 i18n 交给 presentation/interface 联验。已知同源脚本风险必须显式记录，不以保持 URL 证明安全。
- 输入缺失/非法、资源不存在/非 owner、无权限、冲突、DB/文件依赖失败、未知提交、模板不合法要有可区分的应用结果；adapter 按既有 `info.Re`、bool、逐 email map、HTML/JSONP/error 页面形状映射，不得把 DB/文件异常变成空列表、空模板、404 或 `Ok:true`。
- content/admin/interface 的权限、配置、文件和 outbox 都有既定 owner；不得为了本任务局部验收复制另一套规则。当前风险及没有运行过的环境证据须保持明确可见。

## 验收标准

- [ ] AC-PB1：Share/Group 动作清单逐项覆盖 owner/recipient、直接/组、note/notebook、授权变更、撤销/退组、无效输入、并发和投影中断；同级多组 `0+1→1`、全只读 `0+0→0`、个人/笔记优先级不被组内最大值覆盖，撤销可写组后降级或无权限。新建个人/组、note/notebook 授权的逐条可选期限、未填写与旧记录长期有效、旧版改权限不清空已设期限均有回归；界面按使用者时区显示绝对日期时间、跨时区提交后 UTC 比较一致、不出现相对时长预设；显式提交等于/早于服务端当前时刻的期限必须拒绝且不改授权，旧版仅改权限或续期已过期授权须区分省略与显式新期限；仅 owner 显式延长/缩短/取消、已过期 grant 续期成功后恢复、失败/未知提交不误放行、非 owner 不得续期须有负例；受控时钟验证到期前可读/可写、恰在到期点及之后拒绝该 grant、到期后仍存在的其他有效授权可重新合成，以及列表/内容/附件/图片/PDF 不泄露、无需定时清理即可生效；各消费者结果一致，无权者不得看到内容或受邀人资料。期限字段及无效输入负例见 AC-PB1-DATE。
- [ ] AC-PB1-DATE：个人/组 × note/notebook 创建/更新分别覆盖 `expiresAt` 秒级 RFC3339 `Z` 与 `±HH:MM`、跨时区换算及原值读回；拒绝无偏移、空白、小数秒、越界/不存在日期、无效偏移、不晚于服务端当前时刻、`expiresAt` 与 `clearExpiresAt=true` 同传、创建时清除或非法清除标志，且不新增/改变任何授权。省略字段时创建无限期、更新保留原期限；明确 `clearExpiresAt=true` 仅更新并在确认写入后生效；旧版改权、组授权旧 action、多人 email 逐条结果外形兼容。界面按用户时区显示当前值及其时区，输入夏令时跳过/重复时间不得悄悄改期；显式清除与仅留空有区别，旧客户端不带字段行为不变。
- [ ] AC-PB1-SCHEMA：四个集合/收件人类型 partial unique、四个 recipient-leading 索引与 `HasShareNote` 独立唯一投影索引在真实 Mongo 建立并读回 keys/选项；个人/组同资源各一条合法，重复/并发同键不可多条；双收件人、无收件人、零/非法/`null` 值、旧同名索引选项不匹配及历史重复的 preflight 报集合/索引/脱敏键摘要与数量并阻止就绪，不自动修复、忽略或授予权限。
- [ ] AC-PB2：notes/content/image/PDF 从同一 permission port 获取授权结论；未发布、回收站、删除、退组与 DB 失败矩阵一致，且无第二套 grant 判定。
- [ ] AC-PB3：博客发布/取消、批量部分失败、slug/ID、单页/搜索/分类/标签/归档/域名、统计与私有状态都有成功/拒绝测试；USN/receipt 消费 notes 合同。
- [ ] AC-PB4：评论开关、未登录、跨 note 回复、各类删除角色、并发点赞/计数，以及评论与必要通知意图的联合提交、无需通知时仅评论与计数的提交，均有成功/失败/未知提交回归。通知入队失败不留下可见评论或计数、不发信，发送失败保留评论并重试且失败可观测，不误报投递成功；重复/并发及重试不产生重复意图；扩充现有 outbox 的评论事件类型并与 admin 联验，不把仅支持账号事件的现有 `DeliverOutbox` 当作已支持评论。新旧评论中的 `<tag>`、引号和脚本文本在博客/预览/通知邮件中按纯文本显示、不执行；JSON/JSONP 的 `Content` 保持原文本值并按输出上下文转义，不双重编码。评论和回复的纯空白、非法 UTF-8、2001 码点及超过 8192 字节输入均拒绝、不截断、不写入/改变计数/发送通知；2000 码点及合法边界输入可通过，旧评论不被追溯裁剪。对于合法 UTF-8，2000 码点最多 8000 字节，字节上限为附加防护而非可独立触发的边界。
- [ ] AC-PB4-DELETE：评论有权删除与无权/错误删除分别覆盖：取消先赢持久交接闸门，则 pending、retry 及已领取但未交接的事件不得送出；闸门先赢或已发送的消息不承诺撤回，旧 bool 不能把未停用通知误报为已取消；重复删除、删除/领取/交接并发、停用失败及未知提交均不得宣称已成功取消仍可投递的事件。旧评论无需补发通知，删除不泄露已删除正文；确认成功的评论/计数删除沿旧外形，部分/未知保留诊断；admin outbox 终态/取消可观测，内容和错误日志脱敏。
- [ ] AC-PB4-RETRY：评论/回复缺失、空值、非 32 位小写十六进制 `submissionId` 的请求均在业务写入前失败（旧客户端亦然）；浏览器每次有意提交生成新的 128-bit 随机身份，断网/响应丢失后的同次重试保持原身份。相同 actor+身份+note/reply/正文重复提交仅有一条评论、一笔计数和至多一条应通知对象的 outbox 意图，返回同一已确认评论；有意连续两次同文使用不同身份须各自产生独立评论。相同身份但 note、reply 或正文不同须冲突且零副作用；不同 actor 使用同值互不串线、不能读取他人评论凭据。确认成功但响应丢失、并发同键、未知提交/读回错误、无需通知对象、已删除评论后重试（不重建/不发信）均须有服务/DB/真实 HTTP 负例；内部 comment ID 的 outbox 去重不可代替跨请求保证。publishing 的提交凭据、admin 的事件去重及 interface/presentation/delivery 的真实重试证据均未运行前不得标为通过。
- [ ] AC-PB4-RECEIPT-GC：受控时钟证明完整凭据在终态或较晚删除起满 30 天前不可压缩；pending/unknown/未完成对账、未确定 outbox、待重试 dead 不可压缩；终态且 outbox sent/cancelled 后每日有界 500 条 CAS 压缩并读回，重复执行幂等，失败/重启可重试、不越过未确认项。压缩后及长期后同 ID 不重建，已删除只回 deleted/conflict；永久身份索引无 TTL，行数/字节/积压/容量可观测，容量不足显式失败且不淘汰旧身份。
- [ ] AC-PB4-HANDOFF：按 design 全状态表验证合法迁移、非法迁移拒绝、未确认不可领、取消 CAS 赢后已领取 worker 不得用旧正文调用 transport、交接闸门先赢不虚报取消、闸门后崩溃与 SMTP 未知进入 `handoff_unknown` 且不自动重发；确定接受 sent、确定拒绝 retry/dead，已删除正文不得从未知状态补发。对照真实 Mongo/SMTP 竞态、lease 过期、取消失败/读回失败/人工对账和旧账号/feedback outbox 不回退；时间戳不等于 SMTP 接受证明。
- [ ] AC-PB5：三个内置主题、至少一款管理员上传主题及一款普通用户自有 HTML/JS 主题覆盖创建、编辑、图片、ZIP 导入/导出、激活、删除与预览；两类用户上传成功后均可主动激活，持久化 active/ThemeId 一致且各自博客实际渲染。当前登录用户可用未激活的自有主题预览已发布内容，列表/搜索/详情/单页与正式博客共享发布谓词；草稿、撤销发布、回收站或已删除内容在预览中不可见，匿名、他人主题/URL owner 混淆必须拒绝或不泄露，不改变 active/公开状态。导入/激活不自动列入可安装主题，未公开及伪造 themeId 不可被他人安装；管理员可沿既有公开操作将自有主题公开/取消公开，其他已认证用户从公开列表主动安装，复制到自己账户并自动启用，安装后其博客使用独立副本；普通用户不能公开自己的主题。非管理员公开、越权安装、下架后新增安装失败且不破坏旧 active；下架前已安装副本继续可用。恶意路径/链接/容量/模板错误失败无孤儿 active 或公开半包；不为公开当前 active 主题强增旧 UI 没有的入口。

## 已确认合同（2026-09-24）

- **PB-SCHEMA-01：分享期限字段**：`ShareNote`/`ShareNotebook` 使用可选 `ExpiresAt time.Time` / BSON `ExpiresAt`；秒级 UTC DateTime；缺字段永久有效；不使用 TTL 访问控制；历史唯一性冲突阻止静默启动。
- **PB-BLOG-01：`SetNote2Blog` 失败合同**：沿现有 raw boolean 外形执行“全成功 `true`、任一失败/未知/部分写入 `false`”；逐项诊断和修复通过内部 receipt/对账提供。
- **PB-RECEIPT-01：评论提交凭据**：receipt 独立于评论记录，至少持久化 `ActorId`、`SubmissionId`、`NoteId`、`ToCommentId`、正文 SHA-256、`CommentId`、提交状态、删除墓碑、通知意图 ID、创建/更新/确认时间；唯一键为 `(ActorId, SubmissionId)`。完整记录最少保留终态/确认删除较晚者起 30 天；之后只压缩非身份负载，永久保留可回放/拒绝重建的最小凭据。关联 outbox 未确定终态或对账未完成不压缩，不设 TTL；见 PB-02 第 11 条。
- **PB-OUTBOX-01：评论通知状态机**：comment outbox 新增稳定 `CommentId`、recipient identity、`CancelRequested`、`TransportHandedOffAt`、`CancelledAt`、取消原因及版本/CAS 约束。按 PB-02 第 12 条状态迁移；领取不等于交接，删除先赢 CAS 则停发，交接先赢不得声称召回；不确定 SMTP 结果不得自动重发。

## 范围外

不引入后台定时清理作为过期授权判定条件，不默认引入社交功能；不引入 SPA、视觉重设计、新 URL/模板引擎或主题跨域隔离体系。分享持久化到期时间所需的有界字段/旧数据兼容按 PB-01 的 Q-P1 合同执行，除此之外不做无关 Mongo Schema 迁移；不代 identity 实现 Session，不代 HTTP 注册路由，不代 content 写通用存储，不代 admin 发送邮件。不得把旧同源用户脚本风险当作安全验收通过。
