# 技术设计

## 边界与数据流

先从真实路由、控制器/服务调用和浏览器资产入手定位错误，再在现有契约边界内修复。博客页沿现有 controller → service → template 数据流处理；分享沿现有 note/share API 与前端调用处理；Bootstrap 异常只在实际触发的菜单状态转换处修复，不引入第二套 UI 状态管理。

## 诊断顺序

1. 在 Docker 环境复现 `/blog/admin`、博客公开页和分享请求，收集 Leanote 日志、HTTP 状态和非敏感错误位置。
2. 用路由注册和控制器调用链确认博客 500 的共同根因，检查模板数据是否满足现有契约。
3. 追踪分享请求的参数、校验规则和返回映射，补充服务层或适配器层的针对性测试。
4. 在浏览器中复现 `classList` 错误，定位 `dep.min.js` 的源文件/生成来源；修改源文件而不是手改生成资产。
5. 对 PDF 仅做可复现性判断；只有证据确认产品缺陷时才实现修复。

## 兼容与回滚

- 保留现有登录、笔记、搜索和笔记本行为。
- 不修改 `.env`、schema 或持久化卷；测试数据使用可清理的时间标记。
- 每个修复保持小范围提交，出现回归时可按功能独立回滚。
